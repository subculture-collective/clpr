# Release evidence

This directory intentionally contains no passing evidence in source control.
The release operator supplies six JSON files through a protected HTTPS store.
The immutable candidate build supplies `candidate-manifest.json`; copy that
generated manifest unchanged into the same protected store.

The immutable candidate workflow runs automatically on main pushes and remains
available for manual dispatch. It retains the existing source convergence,
image scans, SBOMs, registry digest and cosign checks. Before publication, the
frontend also passes real-container HTTP checks for its served files, metadata,
internal page restrictions and uncached `/build-info.json` source marker. The
required pull-request image gate runs the same checks. The HTTP result is retained
with the candidate evidence as `frontend-http.json`.

After publication, main pushes can deliver only the frontend to the reviewed
Almaz native release through the guarded lane described below. Native service
and schema promotion retain their separate operator evidence requirements.

## Automatic frontend delivery on Almaz

The candidate job signs an additional `frontend-delivery.json` receipt and
Sigstore bundle with the existing production signing key. The receipt binds
the candidate manifest, frontend scan/SBOM/HTTP evidence hashes and the saved
image configuration digest. That digest remains stable when the restricted
receiver converts Docker's OCI archive into a classic import. The receiver
verifies the bundle offline with host-pinned Cosign and public-key hashes,
then compares the imported image with the signed configuration before activation.
A retry retains the first accepted receipt and image content for that revision;
different configuration bytes require a new revision.

Only main-push delivery uses `HOMELAB_WEB_DEPLOY_KEY` and
`HOMELAB_WEB_KNOWN_HOSTS`. The forced SSH command selects the host-owned
`clpr-web` profile and the existing `clpr-frontend` Compose service. It accepts
bounded attestation/image transfers, deployment, status and native verification.
It cannot select a different profile or start the API, crawler or data services.
Manual candidate dispatch continues to build and sign without deploying.

The host contract pins the reviewed backend tree, native release pointer/file,
five API/crawler/data-container identities and images, environment hashes,
mounts, applied migration ledger and schema structure. It also pins the
read-only analytics file and frontend startup, healthcheck, tmpfs and runtime
isolation. The pre-deployment check requires the other four main release gates
and the candidate's completed source, image/signing and receipt steps. Changed
backend source or native state requires a compatibility review before updating
that host contract. The frontend lane runs no migration and creates no passing
operator evidence for native promotion.

The first activation retains root/metadata/favicon checks that also work with
the original markerless image, so automatic image rollback can verify it.
CI separately checks the live source marker with three uncached query variants
and confirms native container start times are unchanged. After independent
first-deployment proof, add the marker as the first image-backed host readiness
check; retain the original readiness profile for recovery to the old image.

Host configuration is `~/.config/fleet-deploy/clpr-web.json`; frontend image and
rollback receipts are under `~/.local/state/fleet-deploy/clpr-web/releases/`.
The native `current` release pointer stays unchanged. Consult the frontend
receipt when assembling a later native release, rather than recreating an older
frontend from the native manifest. Keep native credentials in their existing
private files and deployment diagnostics in the private host state directory.

## Candidate manifest contract

The repository-owned manifest schema is version 1:

```json
{
  "schema_version": 1,
  "candidate_sha": "<lowercase 40-character Git SHA>",
  "backend_digest": "sha256:<64 lowercase hex characters>",
  "frontend_digest": "sha256:<64 lowercase hex characters>",
  "crawler_digest": "sha256:<64 lowercase hex characters>",
  "built_at": "<ISO-8601 timestamp with timezone>"
}
```

`built_at` is the completion time of the immutable candidate image build, not
the workflow start time. The manifest must be generated by the candidate build
and uploaded without hand-editing. Image tags such as `latest`, `main`, or a
release name are not accepted in place of registry digests.

## Operator evidence contract

Every one of the six files must repeat the manifest's exact `candidate_sha`,
`backend_digest`, `frontend_digest`, and `crawler_digest`. Each must also contain
`status: "passed"`, an ISO-8601 `executed_at`, absolute HTTPS `evidence_url`, and
non-empty `owner`. `executed_at` must be later than `built_at` and must not be in
the future. Every boolean declared by the corresponding template must be true.

Evidence-specific assertions are:

- `billing-retirement.json`: free access and absence of paid enrollment verified;
  read-only database and complete provider inventory recorded as counts. Zero
  obligations requires all counts to be zero. Otherwise signed, duplicate and
  out-of-order webhooks, cancellation, invoices, and reconciliation must pass
  through the retained legacy-servicing module. Missing provider credentials
  block this evidence; local empty tables do not prove provider state.
- `hosted-ci.json`: the required candidate workflow passed, branch protection
  requires it, and the supported hosted runner passed WebKit.
- `security-operations.json`: possible JWT exposure was reviewed, affected keys
  were rotated (or rotation was formally found unnecessary), the candidate
  secret scan passed, and every candidate finding was dispositioned.
- `load-and-soak.json`: baseline, stress, soak, and thresholds passed.
- `restore.json`: restore, application smoke, RPO, and RTO passed.
- `rollback.json`: canary, graceful drain, rollback, and post-rollback smoke passed.

Evidence files may contain deployment identifiers and test resource IDs but
must never contain API keys, tokens, customer data, or webhook secrets.

## Verification

The release-readiness workflow must be dispatched from the exact candidate
commit. Configure the repository Actions secrets `RELEASE_CANDIDATE_MANIFEST_URL`
(the complete manifest URL), `RELEASE_EVIDENCE_BASE_URL` (the directory containing
the six JSON files), and `RELEASE_EVIDENCE_TOKEN` (a read-only bearer credential).
Use a separate immutable directory for each candidate SHA. The verifier rejects
a manifest whose SHA differs from the checked-out workflow commit.

For a private certificate authority, configure `RELEASE_EVIDENCE_CA_CERT` with
the PEM CA certificate. This optional public certificate scopes curl trust to
the evidence download step; never disable TLS verification. The store must be
reachable from the hosted runner, reject unauthenticated requests, and expose
only the reviewed evidence objects. Keep its private key and bearer token out
of source control and reports. Record certificate expiry and renew before it
expires. A development-host store is available only while that host is online.

The full source convergence workflow runs on pull requests as well as manual
dispatch. Main branch protection must require the complete Gitea status names
checked by `scripts/verify-gitea-release-controls.sh`; a manually dispatched
run does not supply a pull-request status check.

For an equivalent local check:

```sh
RELEASE_CANDIDATE_MANIFEST=/protected/candidate-manifest.json \
RELEASE_EVIDENCE_DIR=/protected/release-evidence \
RELEASE_EXPECTED_CANDIDATE_SHA="$(git rev-parse HEAD)" \
node scripts/verify-release-evidence.js
```

`RELEASE_EVIDENCE_NOW` is available only to make verifier tests deterministic;
production workflows leave it unset and use the runner clock.

For isolated local HTTPS qualification, load execution accepts
`STAGING_DOCKER_NETWORK` and `STAGING_CA_FILE`; TLS verification stays enabled.
Blue/green execution accepts `CONTAINER_PREFIX`, `DOCKER_NETWORK`, and
`CANDIDATE_CA_DIR` to isolate container names, networking, and certificate trust.
Migrations require TLS (`MIGRATION_SSLMODE`, default `require`).
Protected restores require an executable `APPLICATION_SMOKE_RUNNER`, invoked
with the restored database name and smoke URL. The runner must start the
candidate against that restored database, execute its HTTP smoke, and stop
the temporary runtime before returning so database cleanup can complete.

For a full soak, provide `STAGING_AUTH_FIXTURES_FILE` with per-profile arrays
(`baseline`, `stress`, `soak`), one entry per VU. Each entry contains independent
`member.refresh_token` and `admin.refresh_token` values for disposable users.
The load client rotates these through the real refresh endpoint every 14 minutes.
`STAGING_LOCAL_IPS` selects already provisioned source addresses in the chosen
Docker network namespace, allowing each VU and the rate-limit probe to use an
independent address without changing application abuse controls.
